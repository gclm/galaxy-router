# 重构 SOP

## 为什么需要这个 SOP

AI 自己重构有两个稳定失败模式：

1. **不知道模块真实需求和约束** — 改出来的东西功能不等价
2. **一次吞掉的范围超过上下文承载** — 改到后面忘了前面的约束

本 SOP 在"想优化"和"动手改"之间塞了扫描清单 + 方法库，让 AI 只接自己能稳定做对的活。

## 核心纪律

**行为等价是底线**。一旦会改外部可观察行为 → 不走 refactor，走 feature（需求变）或 issue（bug 修）。

## 复杂度判断

| 复杂度 | 判断标准 | 走哪些 Gate |
|--------|----------|-------------|
| Trivial | 单函数优化，有测试自证 | 不走 SOP，直接改 |
| Simple | 1-3 处优化，有测试 | Gate 2-3 |
| Moderate | 多文件重构 | Gate 0-3 |
| Complex | 跨模块重构 | Gate 0-3（更严格） |

**执行**：判断后告诉用户，用户没反对就执行。

---

## 前置检查（Gate 0 之前）

动笔扫之前先跑一遍，命中任何一条 → **中止，给路由建议**，不要硬凑：

1. **没有测试覆盖** → 先补测试再重构，否则"行为等价"只是口头承诺
2. **范围 > 15 文件或 > 3000 行** → 请用户先缩范围
3. **夹带行为变更** → 不走 refactor，拆出去走 feature 或 issue
4. **是命名偏好/代码风格** → 走 conventions 更新，不走路由
5. **需要跨模块拆分** → 先更新架构文档 + 记决策 + 再做 N 个模块级 refactor
6. **测试不够且无法补** → 风险过高，建议暂缓
7. **实际上是新功能** → 走 feature SOP

零条命中 → 进 Gate 0。扫完真的没发现值得做的就老实说，不凑数。

## Gate 0: 扫描（Moderate+ 必须）

**动作**：
1. 确定扫描范围（哪些文件）
   - 用户点名了文件 → 就扫那些
   - "这个模块" → 模块目录下的文件，不追出边界
   - 范围里要包含测试文件
2. 按方法库扫描优化点：
   - **L1 行为等价迁移**：接口变更用 Parallel Change，整块替换用 Strangler Fig
   - **L2 代码级重构**：超长函数（> 50 行）、重复条件、多层嵌套
   - **L3 结构拆分**：大文件、职责混杂、相同逻辑多份
   - **L4 性能**：重复计算、N+1 查询、大对象无分页
3. 写 `tasks/{slug}/scan.md`（优化点清单）
4. 用户勾选 ✓ / ✗（✗ 写理由）

**退出**：scan.md 用户已勾选

**硬约束**：
- 不允许替用户勾选
- 不凑数（没发现就说没发现）
- 不改行为（只改结构）

### scan.md 格式

```markdown
---
doc_type: refactor-scan
feature: {slug}
status: reviewed
---

# {slug} scan

## 总览
扫描范围：{范围}
发现条数：{N}
建议先做：{哪几条}
慎做：{哪几条}

## 优化点清单

### 1. {一句话描述}
- 分类：L{1-4}
- 位置：{file:line}
- 问题：{具体描述}
- 建议：{方法名}
- 风险：{低/中/高}
```

## Gate 1: 设计（所有复杂度必须）

**前置**：Gate 0 完成（或 Simple 直接跳过）

**动作**：
1. 按用户勾选的条目，设计执行方案
2. 排顺序（有依赖的先做，低风险优先）
3. 每条补：方法号 / 步骤 / 退出信号 / 回滚策略
4. 识别前置依赖（测试覆盖不够的先补）
5. 写 `tasks/{slug}/design.md`
6. 生成 checklist.yaml
7. 用户 review → `status: approved`

**退出**：design.md `status: approved`

---

## Gate 2: 执行（所有复杂度必须）

**前置**：design.md `status: approved`

**动作**：
1. 严格按 checklist steps 顺序
2. 每步完成后做三件事：
   - **跑验证**（测试/类型检查/lint）
   - **行为等价自检**（有没有改了外部行为？）
   - **更新 checklist** status: pending → done
3. 偏离方案 → 停下来汇报，不发挥

**退出**：所有 steps 完成

**硬约束**：
- **一步一做，不批量** — 两步合做意味着出问题不知道是哪步引入的，也回滚不到干净中间态
- 每步都要验证
- 行为等价是底线
- HUMAN 验证项（如前端目视）必须停下来等用户确认，不能用"类型检查过了"替代

### apply-notes 格式

每步完成后记录：

```markdown
## 步骤 N: {动作}
- 改动文件: {file list}
- 验证结果: {测试输出 / HUMAN 确认}
- 行为等价自检: {有无改外部行为}
- 偏离: {无 / 具体描述}
```

---

## Gate 3: 验收（所有复杂度必须）

**前置**：Gate 2 完成

**动作**：
1. 跑全量测试 + 类型检查 + lint
2. 用户目视确认（前端：打开主要页面点一圈）
3. 写 report.md
4. task 归档：`python3 .gclm-harness/tools/task.py finish {task-dir}`

**退出**：用户确认，task 完成

## 方法库速查

| 方法 | 适用场景 |
|------|----------|
| Extract Function | 函数太长（> 50 行） |
| Extract Variable | 复杂表达式 |
| Rename | 命名不清晰 |
| Move Function | 函数放错模块 |
| Split Phase | 函数做两件事 |
| Replace Loop with Pipeline | 命令式循环 |
| Remove Dead Code | 未使用代码 |
| Parallel Change | 接口变更（加新 → 迁移 → 删旧） |
| Strangler Fig | 整块老逻辑被新实现替换 |

---

## 容易踩的坑

- 硬凑清单 — 明显该走其他 SOP 却找理由绕过，扫出一堆"代码可以更优雅"
- 夹带行为改动 — 在重构中间"顺便修了 bug / 优化了提示文案"
- 跨步骤合并动作 — 一次提交做 2-3 步，失去"单步回滚"能力
- 把口味项列进清单 — 命名偏好 / 引号风格 / 箭头函数 vs function
- 没测试覆盖硬上 — "行为等价"只是口头承诺
- 前端效果自己跳过 — AI 看不到，不能用"类型检查过了"替代人工目视
- 扫大模块直接动手 — > 15 文件不拆就进 scan，产出没法决策的长清单
