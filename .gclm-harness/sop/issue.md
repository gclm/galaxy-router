# Bug 修复 SOP

## 为什么需要这个 SOP

修 bug 的直觉是"找到错的地方改了完事"，但这个直觉路径反复制造同样的麻烦：

1. **问题描述只在脑子里** — 改完就忘，三个月后 bug 再现没复现步骤留存
2. **根因没分析就动手** — 改了表面症状，深层问题等下次爆发
3. **修复范围扩散** — 发现一个 bug 顺手改五处引入新问题，无法追溯
4. **没验收闭环** — 怎么判断改好了？改好了什么？没记录

本 SOP 在"看到问题"和"动手改代码"之间塞了缓冲。

## 复杂度判断

| 复杂度 | 判断标准 | 走哪些 Gate |
|--------|----------|-------------|
| Trivial | 明显 typo，一行修复 | 不走 SOP，直接改 |
| Simple | 原因明确，1-2 文件 | Gate 1-3 |
| Moderate | 需要调试，多文件 | Gate 0-3 |
| Complex | 跨模块，根因不明 | Gate 0-3（更严格） |

**执行**：判断后告诉用户，用户没反对就执行。

---

## 快速通道

下面**同时满足**才走快速通道（跳过 Gate 0 和 Gate 1）：

1. AI 读完代码后对根因高度有把握（能指出 file:line + 原因）
2. 修复改动很小（1-2 处）
3. 无跨模块影响风险

快速通道：读代码 → 告知根因 + 方案 → 用户确认 → 修复 → 跑测试 → 写反思。

**不能走快速通道**：根因有多个候选 / 修复涉及多模块 / 需要先复现才能定位 / 用户希望留完整分析存档。

---

## Gate 0: 复现（Moderate+ 必须）

**动作**：
1. 理解问题描述
2. 写复现步骤（能稳定复现吗？）
3. 写 `tasks/{slug}/report.md`

**退出**：问题能稳定复现

**硬约束**：
- 不能复现 → 不修（先解决复现问题）
- 复现步骤必须可执行

### report.md 格式

```markdown
# 问题报告

## 现象描述
{what happened}

## 复现步骤
1. {step}
2. {step}

## 期望行为 vs 实际行为
- 期望：{expected}
- 实际：{actual}

## 环境信息
- {environment details}
```

---

## Gate 1: 根因分析（所有复杂度必须）

**动作**：
1. 从复现步骤出发，追踪代码路径
2. 定位根因（不是症状）
3. 评估影响范围
4. 列出修复方案（2-3 个，推荐一个）
5. 写 `tasks/{slug}/analyze.md`

**退出**：根因明确，方案确定

**硬约束**：
- 不确定根因 → 不修（先继续分析）
- 治标不治本的方案 → 不选

### 根因分析要回答的问题

1. **根因在哪儿？** — file:line + 具体原因
2. **为什么没被早发现？** — 是缺少测试？缺少校验？还是边界条件？
3. **影响范围多大？** — 有没有其他地方存在同样的根因模式？
4. **最简单的修复是什么？** — 改动最小且治本的方案

### analyze.md 格式

```markdown
# 根因分析

## 根因
- 位置：{file:line}
- 原因：{具体原因}

## 影响范围
- 直接影响：{what}
- 可能存在的同类问题：{where}

## 修复方案

### 方案 A（推荐）
- 做法：{what}
- 改动范围：{files}
- 风险：{low/medium}

### 方案 B
- 做法：{what}
- 改动范围：{files}
- 风险：{low/medium}
```

---

## Gate 2: 修复（所有复杂度必须）

**动作**：
1. 按选定方案修复
2. 写回归测试（防止再犯）
3. 跑全量测试确保不破坏其他功能
4. 更新 report.md：修复内容 + 测试覆盖

**退出**：修复完成，测试通过

**硬约束**：
- **必须写回归测试** — 没有"太简单不需要测试"这回事
- 不能引入新问题
- 不在本次修复里顺手改无关代码
- 不夹带新功能

### 修复纪律

1. **只改该改的** — 修 bug 顺手重构是范围扩散的经典路径
2. **回归测试覆盖复现步骤** — 测试用例要能复现原始 bug
3. **跑全量测试** — 修复可能有意外的副作用

---

## Gate 3: 验收 + 反思（所有复杂度必须）

**动作**：
1. 验证复现步骤现在通过
2. 用户确认
3. 反思（**必须写** `memory/reflections/{slug}.md`）
4. 检查是否需要更新 `must/pitfalls.md`（如果这个坑别人也会踩）
5. task 归档：`python3 .gclm-harness/tools/task.py finish {task-dir}`

**退出**：用户确认，反思已写

**硬约束**：
- bug **必须**写反思（防止再犯）
- 反思要具体（不要"下次注意"）

### 反思模板

```markdown
---
doc_type: reflection
date: {date}
feature: {slug}
tags: [{related tags}]
---

# {title} 反思

## Expected vs Actual
- Expected: {what should happen}
- Actual: {what actually happened}

## Root Cause
- {root cause}

## Why Not Caught Earlier
- {how to detect earlier next time}

## Next Time
- {how to avoid, specific and actionable}
```

---

## 容易踩的坑

- 不能复现就硬修 — 猜测性修复成功率极低，还可能引入新问题
- 只治症状不治根因 — 压住报错但根因还在，换个场景又爆发
- 不写回归测试 — "太简单不需要"是下次再犯的前奏
- 顺手改了旁边代码 — bug fix PR 变成综合改动，review 无法聚焦
- 夹带新功能 — "既然改了这里顺便把 X 也加上"，拆出去走 feature
- 反思写空话 — "下次注意"、"加强测试"不解决问题，要写具体的检测方法和防护措施
- 根因分析停在表面 — "变量是 null"不是根因，"为什么是 null"才是
