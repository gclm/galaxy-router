# glm-5.2 限流不换 key 反思

## Expected vs Actual

- Expected:上游限流(账户速率限制)时,应识别为 `KeyRetryable`,自动切换同渠道其他 key 重试
- Actual:智谱 1302 限流只试了 1 个 key 就给客户端 502,另一个 enabled key 没被尝试;最近 3 天 259 次失败

## Root Cause

- 表层:`KEY_NEEDLES`(proxy.rs:137)只有英文 `"rate limit"`,缺中文 `"速率限制"`,中文限流 body 不命中
- 深层:流式路径 `stream_executor.rs:272` 的 SSE 错误提取分支把 status **硬编码为 502**,丢掉上游真实限流语义;换 key 判定只能靠 body 关键词,而关键词表又漏了中文——两层叠加才暴露
- 为什么没早发现:① `KEY_NEEDLES` 按"已知上游特例"枚举,没按"限流/额度/鉴权语义族"系统覆盖中英文;② 流式 SSE 错误归因路径无测试;③ `usage_logs` 记录的是客户端 502 而非上游真实 status,排查易被 502 误导

## Why Not Caught Earlier

- 换 key 单元测试只覆盖 401/402/429 标准状态码 + 英文 body,没覆盖「非标准状态 + 中文 body」
- 流式 SSE 错误提取分支(`extract_error_from_sse` → `UpstreamError{502}`)没有状态码归因测试
- 运行日志对流式路径的上游真实 status 没有打印(`execute_proxy_stream` L187 只 push 到 `AttemptStats`,无 tracing)

## Next Time

- **KEY_NEEDLES 按语义族维护**:限流(rate limit/速率限制/频率限制)、额度(quota/余额/insufficient)、鉴权(unauthorized/invalid key)各覆盖中英文,而非按上游枚举;新增上游时检查语义族是否齐全
- **流式错误归因加测试**:`extract_error_from_sse` / SSE 分支的状态码映射要有单测(阶段 2 做)
- **排查「不换 key」先看判定路径**:从 `is_key_retryable` → `classify_upstream` 反推 status + body 是否命中,不要只盯最终 502
- **运行日志补上游 status**:`execute_proxy_stream` 拿到非 2xx 时打一行 `tracing::warn` 记录真实上游 status(阶段 2/3 顺带)
